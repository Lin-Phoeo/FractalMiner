# 官方后处理 LutBuilder2D 源码抽取(HGRP/PostProcessing/LutBuilder2D)——色调曲线 + 调色 LUT 烘焙

来源:`_dump_1.5.3/AllShader_1.5.3/Assets/packages/com.hg.render-pipelines/runtime/shaders/postprocessing/lutbuilder2d.shader`(47 行)+ `lutbuilder2d\Sub0_Pass0_{Vertex,Fragment}_b{1,2}.hlsl`(全部 2 个变体,**已全文读完**)。

> uberpost 文档(official-postprocess-uberpost.md)已注明"tone 曲线不在本 shader"——**本份补齐那条曲线**。uberpost 只做 `log 编码 → 采样 _LogLut2D → 线性→sRGB 编码(OETF)`,tonemap 算子与全部调色烧在 LutBuilder2D 里。

**本文不含任何单元测试或参考实现**(独立 oracle 由验收方另写),仅忠实转写源码。简写:`f_b1` = lutbuilder2d/Sub0_Pass0_Fragment_b1.hlsl,`f_b2` = …b2.hlsl,`v_b1/b2` = 同名 Vertex。

> **验收修正(Claude 2026-09-28,已逐项对源码核实)**:转写本体几乎零误——ACES 拟合曲线 5 系数 `f_b2:185` **逐位精确**(2.7850849628.../0.107772.../2.9360449.../0.887122.../0.806889),M1/M2/709→AP0/AP0→AP1/AP1→709 矩阵、支点 0.41358840=ACEScc(0.18)、0.93 亮度收敛+高光去饱和均核实无误,f(0.18)=0.10326 复算吻合——**可放心据此复刻**。但三处叙述需更正:
> 1. **ACEScc toe 的 `0.5×` 是标准 ACEScc(S-2014-003),不是 HG 改动**;复刻**必须保留 0.5×,切勿"还原"成 2×**(原稿的"官方 2×"是猜测且错误,虽已 hedge)。"MODIFIED"指的是 `f_b2:185` 的有理拟合曲线 + 0.93 收敛 + 去饱和,不是 toe。
> 2. §0-3 "中灰→0.57×":喂进拟合曲线的 0.18 是**调色后 AP1 值**(非场景线性中灰),仅近中性调色下成立,应标"近似"。
> 3. b1 **不是**"线性 passthrough":它仍跑完整调色链(balance/curves/split-tone/mixer/S-M-H/LGG),只是无 ACES 工作空间 + 无 tonemap,输出未钳制线性。
> **[方向校正 2026-09-30] 原"LUT RT 必为隐式 sRGB / 线性 RT 会压暗"的推断基于把 uberpost 末步误判为"sRGB 解码",实为"线性→sRGB 编码(OETF)"(阈值 0.0031308 + 指数 1/2.4,见 official-postprocess-uberpost.md §4.4 校正),整条推断反了**:uberpost 对 LUT 采样值做**编码**(而非解码),说明 `_LogLut2D` 采样返回的是**线性**调色结果,uberpost 在输出端把它编码为显示域 sRGB。因此 lutbuilder 尾部**无 γ/sRGB 编码指令**(`f_b2:187`/`f_b1:107`)**恰是自洽的**——LUT 存线性、uberpost 编码,不存在"矛盾"。LUT RT 存线性(UNORM/half)即正确;写 sRGB RT 时硬件写编码+采样读解码相互抵消,采回同一线性值,对均值亮度无系统性影响(仅影响精度/banding)。**"skin 偏暗"不能由此机制解释**;真会压暗的复刻错误是"漏掉 uberpost 末步的线性→sRGB 编码"(输出留在线性域→显示偏暗),而非 LUT RT 格式。RT 格式(线性 vs sRGB vs half)仍属 C# 侧、dump 不可判,但已不再是亮度定案的关键 ⚠。

## 0. 对复刻管线的关键提示(先读这个)

1. **本 LUT/UberPost 组合没有独立 tonemap pass**：b2 将该拟合曲线烘进 LUT，b1 没有该 tonemap 算子；这不是全游戏所有管线的排他性结论。uberpost 侧无 TONEMAPPING keyword。
2. **生产端实际 keyword 须由 LUT 生成 draw 的 shader/常量证明**。仅看 LUT 高光 ≤1 不能排他判断 b2：b1 的曲线/调色/资源存储也可能限制值域。帧 6411 已导出消费端 LUT ResourceId19397，但生成端变体绑定仍须追踪。
3. 拟合算子本身 f(0.18)≈0.1033，即约 0.57 倍；这里的 0.18 是完整调色后 AP1 曲线输出，不等于任意场景输入中灰或肤色。不得直接用该比例校准曝光。
4. LUT 与 uberpost 的色彩空间衔接见 §8(**方向已校正:LUT 存线性、uberpost 末步做线性→sRGB 编码**);残留仅 LUT RT 精度/格式 ⚠待核,可截帧确认。

## 5. LUT 像素坐标 → log 编码输入色(两变体相同)

```
u'  = uv - Lut_Params.yz                                   // f_b1:62 / f_b2:62(.yz = 逐轴 UV 偏移,疑为半像素 ⚠待核)
f   = frac(u'.x × Lut_Params.x)                            // f_b1:64 / f_b2:64(.x = 条带数 N)
E0  = float3(f, u'.y, u'.x - f / Lut_Params.x) × Lut_Params.w   // f_b1:65 / f_b2:65 内
```
即 2D 条带坐标展开为 3D 颜色坐标 `(frac(u×N), v, floor(u×N)/N)`,再整体乘 `Lut_Params.w`。**这个 E0 本身就是 log 域编码的输入颜色**(与 uberpost §4.2 的编码同构,见 §8 衔接);`.w` 的 CPU 侧取值(疑为 (N-1)/N 归一)dump 内不可知 ⚠待核。**LUT 尺寸/条带布局由 C# 建 RT 决定,dump 内无属性** ⚠待核。

## 6. b1 = TONEMAPPING_NONE:逐段数学

### 6.1 log 解码(f_b1:65 内层)
```
L0 = (10^((E0 - 0.3860360085964202880859375) × 4.09565830230712890625) - 0.04799599945545196533203125) × 0.17999999225139617919921875
```
注意括号归属:**-0.047996 在 10^x 之后**(线性域减),×0.18 是中灰标定。该式是 uberpost 编码式(`log10(L×5.555556 + 0.047996)×0.244161 + 0.386036`,official-postprocess-uberpost.md §4.2)的严格反函数(已代数验算)。

### 6.2 矩阵三明治 + ColorBalance(f_b1:65)
```
c1 = M1 × (M2 × (L0 × ColorBalance.xyz)) × 5.555555820465087890625
```
矩阵(逐字,M2 行序同源码 float3 构造参数):
```
M1 = [ 2.85846996307373046875  -1.62879002094268798828125  -0.0248910002410411834716796875 ]   // f_b1:65
     [ -0.21018199622631072998046875   1.1582000255584716796875   0.0003242809907533228397369384765625 ]
     [ -0.0418119989335536956787109375  -0.118169002234935760498046875   1.0686700344085693359375 ]
M2 = [ 0.390404999256134033203125   0.549941003322601318359375   0.008926319889724254608154296875 ]
     [ 0.070841602981090545654296875   0.963172018527984619140625   0.001357750035822391510009765625 ]
     [ 0.02310819923877716064453125   0.1280210018157958984375   0.936245024204254150390625 ]
```

### 6.3 log 重编码 + 对比度(f_b1:65)
```
E1 = log10(max(c1 + 0.04799599945545196533203125, 0)) × 0.24416099488735198974609375
    // 源码形: log2(max(c1,0)) × 0.3010300099849700927734375 × 0.24416099488735198974609375,其中 c1 = (L0×ColorBalance)×5.555556 + 0.047996
E2 = ((E1 - 0.0275523960590362548828125) × HueSatCon.z) + 0.0275523960590362548828125
```
即**对比度在"无 0.386036 偏移的 log10 域"绕 pivot 0.0275523960590362548828125 拉伸**。反推 pivot 对应线性值 ≈ 0.2248 【未确认该常量的设计出处】。

### 6.4 解码(无 0.386036 项)+ ColorFilter(f_b1:65)
```
L2 = (10^(E2 × 4.09565830230712890625) - 0.04799599945545196533203125) × 0.17999999225139617919921875
L3 = L2 × ColorFilter.xyz
```
与 §6.1 解码的区别:少减 0.386036(因 E1 本身无该偏移,往返自洽,已验算 E1→L2 还原 L0×ColorBalance×HueSatCon.z 对比度)。

### 6.5 线性 → γ(1/2.2)(f_b1:65 外层)
```
_176 = pow(abs(max(0, L3)), 0.4545454680919647216796875)
```
0.4545454680919647216796875 = 1/2.2(粗 sRGB,非精确分段)。**此后到 §6.8 之前都在 γ 空间**。

### 6.6 SplitToning(γ 空间,f_b1:66-76)
```
w = clamp(dot(clamp(_176,0,1), (0.21267290413379669189453125, 0.715152204036712646484375, 0.072175003588199615478515625)) + SplitShadows.w, 0, 1)   // :66(Rec709 亮度权重)
wS = lerp(0.5, SplitShadows.xyz, 1-w)      // :67
wH = lerp(0.5, SplitHighlights.xyz, w)     // :68
c  = _176; A = 2c; B = 2wS; s = step(0.5, wS)                                                // :69-71
c1 = ((sqrt(c)×(B-1)) + A×(1-wS))×s + (1-s)×(A×wS + c²×(1-B))                               // :72(阴影段,分段软混合)
A' = 2c1; B' = 2wH; s' = step(0.5, wH)                                                       // :73-75
c2 = pow(abs(((sqrt(c1)×(B'-1)) + A'×(1-wH))×s' + (1-s')×(A'×wH + c1²×(1-B'))), 2.2000000476837158203125)   // :76(高光段同式,随后 pow 2.2 回线性)
```

### 6.7 ChannelMixer + Shadows/Midtones/Highlights + Lift/Gamma/Gain(线性域,f_b1:77-82)
```
mix = ( dot(c2, MixerRed), dot(c2, MixerGreen), dot(c2, MixerBlue) )                        // :77
lum = dot(mix, Rec709 权重(同 §6.6))                                                        // :78
wS' = smoothstep(ShaHiLimits.x, ShaHiLimits.y, lum)                                         // :79
wH' = smoothstep(ShaHiLimits.z, ShaHiLimits.w, lum)                                         // :80
g   = ((mix×Shadows)×(1-wS') + (mix×Midtones)×(wS'-wH') + (mix×Highlights)×wH') × Gain + Lift   // :81
o   = sign(g) × pow(abs(g), Gamma.xyz)                                                      // :82(符号保持的逐通道 Gamma)
```

### 6.8 HSV 色相/饱和 + 四曲线(f_b1:83-101)
RGB→HSV 手工展开(:83-94,常数 0.666666686534881591796875、0.3333333432674407958984375、6.0、9.9999997473787516355514526367188e-05):

hue' = hue' + (clamp(CurveHueVsHue.Sample(hue').x,0,1) - 0.5)                                // :96
wrap 到 [0,1](:98);HSV→RGB 标准式(:99,常数 1.0/0.666666686534881591796875/0.3333333432674407958984375/6.0/3.0)
sat  = luma709(hsvRGB) + (HueSatCon.y × (hueVsSat×2 × satVsSat×2 × lumVsSat×2)) × (hsvRGB - luma)   // :101
       // hueVsSat = clamp(CurveHueVsSat(hue).x,0,1);satVsSat = clamp(CurveSatVsSat(sat).x,0,1)
       // lumVsSat = clamp(CurveLumVsSat(dot(_288, Rec709权重)).x,0,1) —— 采样坐标是 §6.7 Gamma 后的 _288 亮度(:101 内)
```

### 6.9 主曲线 + RGB 曲线 + 反归一化输出(f_b1:102-107)
```
n   = (sat × 1/(max3(sat)+1)) + 0.00390625                          // :102(压缩到 [0,1),1/256 偏置)
m   = clamp(CurveMaster(n.r),0,1, 逐通道) + 0.00390625               // :103
r   = clamp(CurveRed(m.r),0,1); g = clamp(CurveGreen(m.g),0,1); b = clamp(CurveBlue(m.b),0,1)   // :104-106
out = max(0, float3(r,g,b) × 1/(1 - max3(r,g,b)))                    // :107(反归一化,可 >1)
```
**b1 输出:未钳制、无 γ 编码指令**。输出色彩空间讨论见 §8。

## 7. b2 = TONEMAPPING_ACES_MODIFIED:逐段数学(与 b1 差异优先)

### 7.1 前段(log 解码 + ColorBalance)
与 b1 §6.1 同式(f_b2:65 内层);随后 `c1 = M1 × (M2 × (L0 × ColorBalance.xyz))`(**无 ×5.555556、无 +0.047996**),M1/M2 同 b1(互逆抵消),再左乘第三矩阵:
```
c1 = M3 × c1,并 clamp(c1, 0, 65504.0)                                     // f_b2:65
M3 = [ 0.4397009909152984619140625   0.3829779922962188720703125   0.1773349940776824951171875  ]   // f_b2:65
     [ 0.08979229629039764404296875   0.813422977924346923828125   0.09676159918308258056640625  ]
     [ 0.01754399947822093963623046875   0.11154399812221527099609375   0.870703995227813720703125 ]

M3 与 ACES 官方 Rec.709→AP0 转换矩阵逐元素一致【已对上 ACES 公开矩阵,行和 ≈1 白点保持】。**即 b2 的调色工作空间 = ACES AP0**。65504 = half 最大值(LUT 目标疑为 half 精度 ⚠待核)。

### 7.2 ACEScc 编码 → 对比度 → 解码(f_b2:66-144)
```
toe 条件: c1 < 3.0517570849042385816574096679688e-05 (=2^-15,逐通道)                          // f_b2:66
编码: toe 段  cc = (log2(1.5258779967552982270717620849609e-05 + c×0.5) + 9.72000026702880859375) × 0.057077623903751373291015625   // :67
      常规段 cc = (log2(c) + 9.72000026702880859375) × 0.057077623903751373291015625           // :68
      // 0.057077623903751373291015625 = 1/17.52;1.52588e-05 = 2^-16
对比度: cc = ((cc - 0.41358840465545654296875) × HueSatCon.z) + 0.41358840465545654296875      // :69
      // pivot = ACEScc(0.18) = 0.4135884(已验算:(log2(0.18)+9.72)/17.52 = 0.413588)
解码(逐通道三分支,f_b2:72-144 三个 do-while 块同式):
      cc < -0.3013698756694793701171875:  L = (pow(2, cc×17.520000457763671875 - 9.72000026702880859375) - 1.52587890625e-05) × 2.0   // :76
      cc < 1.46799647808074951171875:     L = pow(2, cc×17.520000457763671875 - 9.72000026702880859375)                                // :83
      否则:                               L = 65504.0                                                                                   // :88
```

## 8. LUT 输出色彩空间与 uberpost 的衔接 ⚠待核(本份最重要的一处未闭合)

uberpost 链(official-postprocess-uberpost.md §4.2-4.4,已验收):场景色 → 曝光 → **log 编码**(与 §6.1 解码严格互逆,已验算)→ 采样 `_LogLut2D`(t2,space3,f_b288:179)→ **线性→sRGB 编码 / OETF**(0.003130800090730190277099609375 / 12.9200000762939453125 / 0.4166666567325592041015625 / 1.05499994754791259765625 / 0.054999999701976776123046875;阈值 0.0031308 + 指数 1/2.4 = OETF,**编码非解码**)→ 抖动。注意 uberpost 的 `_Lut_Params` 是 uberpost 自有 cb0 槽(f_b288:148-176),与本文 `ColorGradingCB.Lut_Params`(b9 c2)**不是同一缓冲**,勿混用。

矛盾点(**[方向校正 2026-09-30] 此"矛盾"实际不存在**):原文认为 lutbuilder 尾部无显式 γ 编码指令(b1:107 / b2:187)、而 uberpost 却对 LUT 采样"解码",故推断"LUT 内容必须是 sRGB 编码的"。但 uberpost 末步是**线性→sRGB 编码(OETF)而非解码**(见 §0 校正框与 official-postprocess-uberpost.md §4.4)——所以正确图景是:**LUT 存线性调色结果,uberpost 在输出端编码为显示 sRGB**,两者本就自洽,lutbuilder 尾部不做 γ 编码正是对的。故 LUT 纹理内容应为**线性**,而非 sRGB。以下原推断的两种"sRGB 机制"已作废,仅保留作历史记录:
- ~~(a) LUT RT 为 sRGB 格式,写入时硬件隐式编码~~(即便用 sRGB RT,写编码+读解码相互抵消,采回线性值,不改变链路语义);
- ~~(b) 四张 ramp 纹理数据本身为显示域编码~~(与"uberpost 编码"叠加会双重编码→偏亮,反而不自洽)。
dump 内无法看到纹理内容/RT 格式 ⚠待核,可截帧确认精度/格式;但**方向已定案(LUT 线性、uberpost 编码)**,RT 格式仅关精度与 banding,不再是亮度定案关键。若复刻整体偏暗,先查是否漏了 uberpost 末步的线性→sRGB 编码,而非 LUT RT 格式。
